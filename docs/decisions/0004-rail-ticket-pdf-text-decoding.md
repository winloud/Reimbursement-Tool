# ADR 0004：铁路电子客票 PDF 文本解码与中转分组路线

## 状态

已采纳。

## 背景

部分铁路电子客票 PDF 使用 `/GBK-EUC-H` 等预定义 CMap，中文字体没有 `/ToUnicode`。常规 PDF 库可能先把字符串错误转换为 Unicode，导致程序提取乱码，但阅读器仍可依靠内置 CMap 正常复制中文。车票导入只需要可靠获得出发站、到达站和乘车日期，不需要发车时间。

## 决策

- 从 PDF 内容流读取文本对象的原始字节，根据每段文字所用字体的 `/ToUnicode` 或 `/Encoding` 解码。
- 支持 GBK、GB18030、GB2312、UTF-16BE 以及 pypdf 已知的标准单字节和 Big5 映射；未知编码不猜测。
- 不引入 OCR，不使用英文站名或英文别名回退；中文站名无法恢复时由用户在预览中人工填写。
- 车票候选和确认接口不保存发车时间，生成行程的出发、到达小时均为空。
- 多票首次预览时先按乘车日期和站点连接关系自动整理：仅当一个连接分量构成唯一的简单有向路线时按路线重排；存在分叉、多前驱或循环时保留该分量的上传顺序，不强行猜测。
- 自动整理后，站点连续且日期为同日或次日时默认合并。若下一票到达已经访问过的站点，则在该票之前拆分，作为明显返程或路线回环处理；用户进入预览后仍可手动调整顺序或拆分。

## 依据

- 已检查的铁路票样本中，中文字体使用 `/GBK-EUC-H` 且缺少 `/ToUnicode`，原始字符码仍可按 GBK CMap 恢复。
- PDF 阅读器可以正常复制中文，证明文字信息存在，问题在解析库的字符映射路径而非票面图像质量。
- 原始字节解码比 OCR 更稳定、速度更快，也不会增加模型、运行库和发布包体积。
- 文件选择顺序通常受文件名或系统选择行为影响，不能作为实际乘车顺序的可靠依据；日期与精确站点连接可在无歧义链条中恢复路线顺序。

## 后果

正向影响：

- 中文站名不依赖有限的英文别名表。
- 不增加运行依赖或安装包体积。
- 无图像识别误差，无法解码时会明确要求人工修正。

代价：

- 需要维护字体编码和内容流文本矩阵解析。
- 未知、自定义或损坏的字符映射无法自动恢复。
- 不读取时间后，同日同站点出现分叉时无法可靠判断先后，因此只自动整理唯一简单路线；歧义场景仍需用户调整。
