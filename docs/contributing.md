# 协作与提交规范

## Git 提交信息

所有提交必须遵循 Conventional Commits：

```text
<type>(<scope>): <description>
```

- `type` 必填，使用小写英文：`feat`（新增用户可见功能）、`fix`（修复问题）、`docs`（文档）、`style`（不改变行为的格式或样式）、`refactor`（重构）、`test`（测试）、`build`（构建或依赖）、`ci`（持续集成）、`chore`（其他维护）或 `perf`（性能）。
- `scope` 可选，用于指出受影响区域，例如 `report-edit`、`ticket-import`、`backend`、`release` 或 `docs`。
- `description` 必填，简洁说明实际改动；可使用中文或英文，不使用含糊的“更新”“修改”等描述。
- 每个提交只包含一个完整、可验证的逻辑改动；混合工作区时只暂存本次提交涉及的文件。
- 不兼容变更在类型或范围后追加 `!`，并在提交正文中补充 `BREAKING CHANGE:` 说明。

示例：

```text
feat(ticket-import): 支持粘贴铁路电子客票 PDF
fix(report-edit): 修复日期输入框截断
docs(contributing): 说明提交信息规范
chore(release): publish v1.2.5
```

## 验证触发条件

开发和合并前按改动影响选择检查，不因“合并”一律运行全量。组合验证统一使用 `scripts/verify.ps1 -Profile <档位>`：

| 改动或任务 | 验证要求 |
| --- | --- |
| 纯文档、注释或文案整理，不改变运行行为 | 检查 diff、链接及命令与现有入口是否一致，运行 `git diff --check`；不要求全量测试或构建。若已有测试直接约束所改文档，运行该定向测试。 |
| 后端业务或数据逻辑 | 开发中运行相关回归测试；需要后端整体验证时用 `Backend`。涉及迁移、金额或附件数据时覆盖对应风险场景。 |
| 前端行为或布局 | 使用 `Frontend`（前端测试与生产构建）；布局、交互变化补充相关页面人工检查。 |
| Tauri 桌面壳或权限配置 | 使用 `Desktop`（配置与权限静态检查、Rust 单测、clippy）；安装、迁移、更新行为按影响补充实际环境验收。 |
| 构建、签名、发布脚本或 workflow | 使用 `Release`（`tests/release`、PowerShell 语法及 Git 空白检查）；构建或交付行为变化还需相应产物验证。 |
| 跨领域且影响范围难以隔离，或正式发布前 | 使用 `All`，并补充本次涉及的安装、升级或迁移验收。 |
| 本地测试包或本地正式包 | 使用[发布流程](release-process.md#按任务选择入口)指定入口，由入口执行既定检查；无需为启动构建预先手动再跑同一档位。 |

`Backend` 运行全量 pytest，包含 `tests/release`；`All` 在此基础上执行前端、Desktop 和发布静态检查，已覆盖 `Release` 的检查范围。通过 `All` 后无需再单独运行 `Release`。

开发和合并阶段，源码、依赖及相关环境未变且结果可追溯时，可复用已通过的检查；发生变化后重跑受影响部分。正式构建、发布脚本和 CI 自带的门禁照常执行，不因本地已通过而默认添加跳过参数。未运行的检查及原因写在任务完成说明中，不把自动化流水写进当前计划。
